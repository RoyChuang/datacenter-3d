# 新案場：從平面圖到 3D 初版

固定流程，每個案場都一樣。只有第 2 步需要「看圖」（人或 AI），其餘都是程式。

**只能產生 `sites/<id>/` 底下的檔案。** `src/generated/` 由 `npm run sites` 產生，手寫的 JSON 不會經過驗證，也無法重現。

```
plan.png ──(2. 看圖填寫)──▶ site.yaml ──(3. 編譯 + 驗證)──▶ src/generated/<id>/*.json ──▶ 3D
                                ▲                                                    │
                                └──────────────(4. 疊圖比對，修正 yaml)───────────────┘
```

## 1. 建立案場資料夾

```
sites/<案場id>/
  plan.png      平面圖（png / jpg / webp）
  site.yaml     複製 sites/dc-1f/site.yaml 改
  devices.json  （選用）真實的機櫃內容，有的話會取代假資料
  notes.md      判讀紀錄：比例怎麼量的、圖例怎麼解讀、哪些已確認、哪些還是假設
```

`notes.md` 參考 [sites/dc-1f/notes.md](../sites/dc-1f/notes.md)。每次和使用者確認過的答案都要更新進去。

**判定依據、量測數據、待確認事項一律寫在 `notes.md`。** `site.yaml` 的 `props` 會原樣顯示在詳情面板，只放要給使用者看的設備屬性（例如 `alias`、`capacityKVA`、借用類型時的 `kind`），不要逐台寫判定說明。

`mockDevices`：沒有 `devices.json` 時維持 `true`，否則機櫃內是空的。

`<案場id>` 只用英數和 `-`，且要和 `site.yaml` 裡的 `id` 相同。

## 2. 看圖，填寫 site.yaml

依這個順序填，每一步都有對應的檢查：

| 步驟 | 要做的事 | 怎麼確認 |
|---|---|---|
| 2.1 比例 | **用程式量**平面圖上一格地板幾像素 → `plan.pxPerTile`；**橫向、縱向分開量**；房間幾格寬、幾格深 → `grid` | 量測數據寫進 `notes.md`；兩個方向差超過 3% 時重新取樣底圖（見下方「比例」） |
| 2.2 圖例 | 列出圖上所有顏色和符號代表什麼；**看不懂的先問，不要猜** | — |
| 2.3 排 | 一排一排記下：方向、中心線、起點、朝向、依序的編號（見下方「定位基準」） | 編號不連續會出現警告；每排頭尾都要對齊 |
| 2.4 尺寸 | 每台設備依「尺寸判定標準」決定寬度 → `widths` / `equipment.width` | 疊圖時每台的中心、每排的頭尾都要對齊 |
| 2.5 牆與門 | 牆寫成矩形；門寫在 `doors`，會自動把牆切開（見下方「牆與門」） | 疊圖時牆、門的位置都要對齊 |
| 2.6 封閉通道 | 指定是哪兩排，系統自動算範圍 | 兩排之間沒有空間會報錯 |
| 2.7 點位 | 感測器、攝影機的位置（格） | 疊圖時圖示對齊 |
| 2.8 電力拓樸（選用） | UPS → PDC 的 A/B 路、備援配對、每台 PDC 供電給哪幾排 → `power`（見下方「電力」） | 編譯會檢查迴圈、找不到的編號、假備援 |
| 2.9 冷卻方式 | 封閉的是冷通道還是熱通道 → `airflow` | 未設定或不支援時，氣流圖層不顯示（會有警告） |
| 2.10 展示資料（選用） | 要不要固定幾個偏熱的感測器 → `mock.hotSpots`；沒有額定功率但要展示容量視圖的電力模式 → `mock.ratedKW` | 編號不存在會有警告 |
| 2.11 機櫃額定功率（選用） | 每台機櫃的可用功率預算 → `types.rack.ratedKW` / `ratedKW`（見 site-format.md） | 平面圖看不出來，**一定要問**；沒有答案就不要填 |

座標換算：`格 = 像素 ÷ pxPerTile`（如果 `originPx` 不是 0，要先減掉）。

### 比例：橫向、縱向分開量

監控軟體的截圖常常被拉伸，地板格看起來不是正方形。**不要用看的估**：模型看到的圖片會被縮小，分辨不出 24 px 和 27 px 的差別。寫一段程式讀像素：橫向、縱向各取 10 條以上的格線，用線性擬合算間距和殘差。

格線被設備蓋住、量不準時（同一張圖不同區域差到幾 %），改用一排已知尺寸的設備從頭量到尾來核對，例如 10 台 600 mm 寬的機櫃。截圖裡平面圖不在左上角時（旁邊有面板、標題列），用 `originPx` 填平面圖格座標 (0,0) 的像素位置。

- 兩個方向差不到 3%：取平均，填一個 `pxPerTile`
- 差超過 3%：格式只能填一個數字，**不要硬用其中一個方向的值**。否則另一個方向的公尺數會整個縮放，疊圖時卻因為資料和底圖用同一個比例，仍然會「看起來對齊」，問題完全被藏住。
  - 先用設備核對哪個才是真的：例如機櫃沿排的間距在兩個方向換算都是 600 mm，代表地板格其實是正方形、只是截圖被拉伸
  - 確定是截圖拉伸時：原圖改名為 `plan-original.png` 保留，把底圖**重新取樣**成正方形格（放大比較小的那個方向），存成 `plan.png`；`pxPerTile`、`originPx` 用重新取樣後的值
  - 無法判斷哪個方向正確時：停下來，把兩個方向的數值寫進 `notes.md`，回報給使用者

`notes.md` 的「比例」一節**必須**寫出以下數據，沒有就不算完成：

- 橫向、縱向各用了幾條格線、擬合出的間距（px）、最大殘差
- 用哪一排已知尺寸的設備核對，結果幾 px
- 最後填的 `pxPerTile`、`originPx`，以及有沒有重新取樣底圖
- 換算後房間幾 × 幾公尺

### 尺寸合理性檢查

疊圖不能證明比例正確，所以要另外用公尺數反算，寫進 `notes.md`：

- 排距、通道寬：例如機櫃深 1200 mm、排距 4 格，通道就是 1.2 m。機櫃之間的通道一般在 0.9～1.8 m，算出來不在這個範圍，多半是比例錯了
- 房間尺寸和設備數量是否相稱

### 尺寸判定標準

每台設備的寬度都照下面的順序判定，**用第一個成立的來源**，並在 `notes.md` 記錄用的是第幾級：

| 級 | 來源 | 適用 | 填法 |
|---|---|---|---|
| 1 | 使用者確認的規格、`devices.json` 或其他真實資料 | 任何設備 | 照實填 |
| 2 | 同一排**相鄰設備的中心間距** | 排裡的設備 | 間距換算成 mm，取最接近的 50 mm；和預設寬度差 10% 以內就用預設 |
| 3 | **圖示外框** | 單獨放置、無法量間距的設備 | 外框換算成 mm，取最接近的 100 mm |
| 4 | `site-format.md` 的類型預設 | 圖示只是符號（明顯比任何真實設備都小） | 不填，用預設 |

深度：一律用類型預設，因為圖示的深度最不可靠；第 3 級量到的外框深度只記在 `notes.md`。

判定原則：

- 平面圖上的空隙通常只是畫面留白；**不要為了疊圖貼齊而縮小設備或加 `gap`**，`gap` 只用在確定有空位的地方
- **驗收標準**：疊圖時每台設備的中心、每排的頭尾，都要和圖示對齊（誤差 0.2 m 內）。對不上代表判定錯了，回頭重判；判不出來就列成問題，不可以留著不一致的結果交差
- 判定結果和其他資訊矛盾時（例如用預設深度讓通道窄得不合理），**列成問題問使用者**，在 `notes.md` 記錄兩種數值
- 第 2、3 級得到的尺寸都是推定，在 `notes.md` 標為待確認
- 單獨放置、靠牆的設備，正面朝向背離牆面

### 定位基準

座標一律從圖上**量出來的點**換算，不可以沿用其他排或其他設備的值：

- **排的中心線 `line`**：該排所有設備中心的平均
- **排的起點 `from`**：由該排**第一台設備的中心**回推，`from = 第一台中心 − 第一台寬度 ÷ 2`。寬度改過（例如第 2 級判定成非預設寬度）就要重算；不可以因為別排從 4 開始就填 4
- 填完後用最後一台核對：`from + 寬度總和` 要等於最後一台圖示的尾端（誤差 0.2 m 內）
- **單獨設備 `at`**：圖示外框的中心

### 未確定的值

- **選填欄位**（`airflow`、`power`、`aisles`、`points` 等）看不出來就**不要填**，列成問題。不可以填一個推測值，例如 `airflow: none` 等於斷言沒有封閉通道
- **必填欄位**（例如排的 `facing`）沒有依據時，用一個值並在 `notes.md` 標為待確認

### 數量對帳

`notes.md` 必須有「數量」一節，逐類列出**圖上數量**和**建模數量**，每一個差異都要寫原因（例如「不建模：使用者確認」「列為問題：用途不明」）。

- 圖上看得到編號或可辨識的設備，**不可以默默省略**
- 被浮層、文字、其他圖示遮住一部分的設備：能從看得到的部分和同類設備推定位置與尺寸時，照推定建模，在 `notes.md` 標為推定；推定不了就列成問題
- 完全看不到的內容不要補造

### 牆與門

- **牆的座標取牆線本身**：雙線牆取兩條線的範圍，單線牆取線的位置，換算成格。房間的外框、隔間都照這個方法量
- 每個門都要落在一面牆上（外牆或 `walls` 裡的牆）。門弧**只用來判斷門在哪面牆、門寬多少**，不能當成座標：門的 `rect` 和它所在的牆線重疊，長邊和牆同方向，長度是門弧的弦長
- 圖上封閉的房間（隔間、坡道間等），3D 也要封閉：每一面牆都要建，門只切開門的部分
- 柱子、牆的凸出**看得到就要建**，用 `walls` 的矩形表達；用途不明時照建，在 `notes.md` 標為待確認

### 格式不夠用時

照現有格式盡量表達，**不要自行修改程式或格式，也不要自創 `site-format.md` 沒有的欄位**（程式不會讀，畫面上也不會出現）。例如沒有對應的設備類型，可以借用相近的類型，並用 `props.kind` 標示。在 `notes.md` 記錄缺了什麼，回報時列出來。

### 電力（2.8）

平面圖通常看不出接線，**這一段幾乎都要問人**，不要從圖上推測：

- 哪台 UPS 是 A 路、哪台是 B 路（寫在 `props` 的 `alias`，例如 `UPS1: { alias: UPS-A }`）
- 每台 PDC 接在哪台 UPS 下面（`feeds`）
- 哪些 PDC 互為備援（`redundancy`）；一台 B 路 PDC 可以同時備援兩台 A 路 PDC
- 每台 PDC 供電給哪幾排（`serves`，寫排名稱代表整排的機櫃和列間空調）
- 圖上有、但沒有數值可顯示的設備（例如電表、電池、配電箱），問要不要建模；不建模就不要寫進 site.yaml

沒有迴路資料、只能依位置推定時，設 `servesAssumed: true`，畫面會標示「推定」。

### 熱圖與氣流（2.9）

- **溫度熱圖**：不用設定，有感測器就會產生（以安裝高度的水平切面呈現）
- **氣流**：只在 `airflow: cold-aisle` 時產生，前提是**冷通道封閉＋列間空調**，氣流方向由排的朝向和封閉通道推算。熱通道封閉（`hot-aisle`）或沒有封閉（`none`）目前不支援，圖層會自動不顯示，不會畫出錯的方向
- 封閉的是冷通道還是熱通道，**一定要問**：兩者氣流方向剛好相反，也會影響機櫃朝向的判讀

### 交給 AI 做時的指示

> 依照 `docs/workflow.md` 第 2 步和 `docs/site-format.md`，看 `sites/<id>/plan.png`，產生 `sites/<id>/site.yaml`。
> 用 `sites/dc-1f/site.yaml` 當範例。只輸出排與順序，不要逐台估座標。
> 看不懂的圖例、無法確定的朝向，先列成問題問我。
> 比例要寫程式讀像素，橫向、縱向分開量，數據寫進 notes.md；兩個方向不同時照「比例」一節處理，不要只用其中一個。
> 只寫 `sites/<id>/` 底下的檔案，不要手寫 `src/generated/`；只用 site-format.md 有的欄位。
> 設備尺寸以真實規格為準，不要為了疊圖貼齊而縮小設備或加 gap；圖示和規格矛盾時列成問題。
> 不要修改程式或格式；格式不夠用的地方寫進 notes.md 並回報。
> 完成後執行 `npm run sites`，修正所有 ✖ 錯誤，並在回報中列出所有 ⚠ 警告。
> 把判讀依據、已確認和尚未確認的假設寫進 `sites/<id>/notes.md`。
> 完成前逐項核對「交件檢查清單」，缺一項就不算完成。
> 電力拓樸、冷卻方式（冷通道／熱通道封閉）、機櫃額定功率從圖上看不出來，先列成問題問我，不要推測。

## 3. 編譯與驗證

```bash
npm run sites
```

| 標示 | 意思 | 例子 |
|---|---|---|
| ✖ 錯誤 | 必須修正，否則不會輸出、`npm run build` 也會失敗 | 設備重疊、編號重複、通道沒有空間、排的方向寫錯 |
| ⚠ 警告 | 要人確認 | 編號不連續、設備超出房間、壓到牆、`widths`/`props` 的編號打錯、機櫃沒有額定功率 |

`npm run dev` 執行時，存檔 `site.yaml` 會自動重新編譯並更新畫面。

## 4. 疊圖比對

`npm run dev` → 瀏覽器開 `?site=<案場id>` → 按「俯視」→ 勾「平面圖疊圖」。

逐區檢查：每排的頭尾、單獨設備、**牆、門**、通道、點位都要和圖對齊。不對就改 `site.yaml` 存檔，畫面會自動更新。

注意疊圖**不能證明比例正確**：資料和底圖用的是同一個 `pxPerTile`，比例填錯時兩者會一起縮放，看起來仍然對齊。要另外確認：

- 3D 地板格和圖上格線，**橫向、縱向都要**對齊
- 房間換算成公尺後的尺寸合理（可以和已知的機櫃數量、通道寬度對照）
- 疊圖貼齊是因為設備用了真實規格，而不是因為把設備尺寸改成圖示的大小

## 交件檢查清單

以下全部成立才算完成，缺一項就是未完成，不可以回報完成。**驗收沒過要先修正再檢查**，只有修正後仍做不到（例如格式不支援）才列為問題回報，並寫明試過什麼：

- [ ] `sites/<id>/site.yaml`、`sites/<id>/notes.md`、平面圖都在
- [ ] `notes.md` 有「比例」（含量測數據）、「尺寸」（每類設備用第幾級判定）、「數量」（對帳）、「尚未確認的假設」、「問題」各節
- [ ] `npm run sites` 沒有 ✖；所有 ⚠ 都抄進回報
- [ ] 疊圖逐區檢查過：設備、牆、門都對齊（誤差 0.2 m 內）
- [ ] `props` 沒有判定說明；`mockDevices` 沒有真實資料時是 `true`

## 5. 需要人確認的清單（每個案場都要問）

- 機櫃正面朝向（平面圖常常沒有標）
- 灰色或不明區塊是牆、柱子還是空位
- 看不懂的設備代號
- 機櫃高度（預設 42U），有沒有不同規格
- 機櫃深度：圖示的深度常常不是實際比例，和通道寬度矛盾時要問
- 同一種設備用不同顏色時，顏色代表規格、用途還是狀態
- 圖上沒有標示門時，門在哪裡
- 地板格不是正方形時（見第 2 步「比例」），實際比例怎麼處理
- 封閉的是冷通道還是熱通道（決定氣流方向，也影響機櫃朝向）
- 電力：哪台 UPS 是 A / B 路、PDC 接在哪台 UPS、備援怎麼配、每台 PDC 供電給哪幾排
- 機櫃額定功率（可用預算，已扣降額；雙路時為單路容量）：全場一樣，還是依排或單台不同
- 圖上有但沒有數值的設備（電表、電池、配電箱等）要不要建模
