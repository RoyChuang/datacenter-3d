# 設計紀錄

記錄這個專案「為什麼這樣做」，以及目前驗證到什麼程度。使用方式請看 [workflow.md](workflow.md)。

## 目標

拿到任何案場的平面圖（通常是監控軟體的截圖），都能用**固定的流程**穩定產生 3D 機房的初版。

## 關鍵決策

### 1. 看圖的結果寫成 site.yaml，不直接產生座標

第一版是逐台估出像素座標再換算，每換一張圖結果都會不同，而且很難檢查。
改成只描述「排」：方向、中心線、起點、朝向、依序的編號，座標由程式算。

- 看圖時要判斷的事情變少，主要只剩順序和朝向，比較不會錯
- 人看 yaml 就能檢查，跟看圖的方式一樣
- 同一份 yaml 產生的結果每次都一樣

### 2. 位置用「地板格」，尺寸用 mm

- 平面圖上最可靠的參考是地板格線，看圖時用格來數最直接
- 設備規格習慣用 mm（600 / 800 / 1200）
- 兩種單位刻意分開，一看就知道是位置還是尺寸
- 換算一律交給編譯器處理（`tileSize`）

### 3. 能自動推算的就不讓人填

- 封閉通道：指定是哪兩排，範圍、頂板、端門自動算
- 門自動切開牆：牆畫成一整條，放上門就好
- 設備類型由編號判斷：`R1` → 列間空調、`PDC` → 配電櫃
- 點位編號自動產生

人填的東西越少，出錯的機會就越少。

### 4. 驗證分成兩層

- **程式驗證**（`npm run sites`）：重疊、重複、超出範圍、通道沒空間、編號不連續、覆寫的編號打錯
- **疊圖比對**（瀏覽器勾「平面圖疊圖」）：抓程式抓不到的問題，例如朝向填反、圖例認錯、比例量錯

錯誤（✖）會讓 build 失敗，所以有問題的資料不會被部署上線。

### 5. 產生的 JSON 不進版控

`src/generated/` 在 build 時由 Vite plugin 產生。唯一的資料來源是 `site.yaml`，不會出現 yaml 和 JSON 對不上的情況。

### 6. 為什麼不是做成 skill

需要穩定的是流程本身，所以放在 repo 裡：用程式加文件，人和 AI 都照同一套走。
之後如果要做 skill，也只是用來「呼叫這個流程」。

### 7. 機櫃高度

預設 42U：42 × 44.45 mm，加上下各 65 mm，約 1997 mm。可以在 `site.yaml` 的 `types.rack.uHeight` 覆寫。

## 已知限制

- 排只支援橫排和直排，不支援斜放
- 房間只支援矩形；不規則形狀要用牆去拼
- 沒有柱子、樓梯這類物件，暫時用牆的矩形代替
- 一個案場只能有一層樓
- 平面圖品質影響很大：軟體截圖最好，照片或手繪圖誤差會比較大
