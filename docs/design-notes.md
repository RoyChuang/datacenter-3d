# 設計紀錄

記錄這個專案「為什麼這樣做」，以及目前驗證到什麼程度。使用方式請看 [workflow.md](workflow.md)。

## 目標

拿到任何案場的平面圖（通常是監控軟體的截圖），都能用**固定的流程**穩定產生 3D 機房的初版。

## 關鍵決策

### 1. 看圖的結果寫成 site.yaml，不直接產生座標

第一版是逐台估出像素座標再換算，每換一張圖結果都會不同，而且很難檢查。
改成只描述「排」：方向、中心線、起點、朝向、依序的編號，座標由程式算。

- 看圖時要判斷的事情變少，主要只剩順序和朝向，比較不會錯
- 人看 yaml 就能檢查，跟看圖的方式一樣
- 同一份 yaml 產生的結果每次都一樣

### 2. 位置用「地板格」，尺寸用 mm

- 平面圖上最可靠的參考是地板格線，看圖時用格來數最直接
- 設備規格習慣用 mm（600 / 800 / 1200）
- 兩種單位刻意分開，一看就知道是位置還是尺寸
- 換算一律交給編譯器處理（`tileSize`）

### 3. 能自動推算的就不讓人填

- 封閉通道：指定是哪兩排，範圍、頂板、端門自動算
- 門自動切開牆：牆畫成一整條，放上門就好
- 設備類型由編號判斷：`R1` → 列間空調、`PDC` → 配電櫃
- 點位編號自動產生

人填的東西越少，出錯的機會就越少。

### 4. 驗證分成兩層

- **程式驗證**（`npm run sites`）：重疊、重複、超出範圍、通道沒空間、編號不連續、覆寫的編號打錯
- **疊圖比對**（瀏覽器勾「平面圖疊圖」）：抓程式抓不到的問題，例如朝向填反、圖例認錯、比例量錯

錯誤（✖）會讓 build 失敗，所以有問題的資料不會被部署上線。

### 5. 產生的 JSON 不進版控

`src/generated/` 在 build 時由 Vite plugin 產生。唯一的資料來源是 `site.yaml`，不會出現 yaml 和 JSON 對不上的情況。

### 6. 為什麼不是做成 skill

需要穩定的是流程本身，所以放在 repo 裡：用程式加文件，人和 AI 都照同一套走。
之後如果要做 skill，也只是用來「呼叫這個流程」。

### 7. 機櫃高度

預設 42U：42 × 44.45 mm，加上下各 65 mm，約 1997 mm。可以在 `site.yaml` 的 `types.rack.uHeight` 覆寫。

### 8. 電力拓樸（2026-10-17）

- 拓樸寫在 site.yaml 的 `power`，編譯時檢查迴圈、斷線、假備援
- 3D 只畫機房內的設備；平面圖上沒有的上游可以用 `external` 顯示成來源標籤。dc-1f 的 EMP 電表位置不明、也沒有數值，所以不納入，UPS 就是起點
- UPS → PDC 畫線；PDC → 機櫃用「上方匯流排」呈現：沿著每排拉一條幹線，再往下接到每台機櫃，A、B 分在機櫃頂部兩側（2026-10-17 使用者要求畫出，原本只上色）
- 點選時把供電範圍內的機櫃上色，並亮起相關的幹線
- 列間空調也在電力鏈上：和機櫃一樣接在同一條匯流排上，由該區的 PDC 雙路供電（推定）；電力畫面中也和機櫃一樣淡化，點選時才突顯
- 走線是示意：畫在機櫃上方，A、B 分在不同高度，不代表實際路徑
- A 路藍、B 路橙、直流灰；單路供電不特別標示（使用者決定，2026-10-17）
- dc-1f 的 PDC 供電範圍目前是依位置推定（`servesAssumed`），面板會標示「推定」

### 9. 場景操作與效能（2026-10-17）

- **按需重繪**：只有鏡頭移動、資料或圖層變化時才畫；靜止時約每秒 1 次（只有感測器更新）。電力圖層的流動動畫限制在約 30 fps。原本不論有沒有動都持續重繪，是 Mac 卡頓的主因
- **溫度標記**：感測器上方的圓點固定螢幕大小、畫在最上層；正常是小綠點，警告（橙）和告警（紅）稍大。數值不常駐顯示（使用者決定，2026-10-17），只在滑鼠提示和詳情面板中出現
- **選取外框**：粗的琥珀色外框，畫在最上層，被牆或鄰近設備擋住也看得到
- **雙擊聚焦**：鏡頭站在設備正前方約 3.2 m；冷通道太窄，中間的對面那排暫時變半透明（剖切），取消選取後恢復。若正前方 3.2 m 落在設備或牆裡，會往回找空位

### 10. 溫度熱圖（2026-10-17）

- 感測器安裝高度（1.6 m）的一片水平溫度圖，以距離加權內插感測器的即時讀數，每次資料更新重算
- 色階 15～35 °C（使用者指定）；黃色對齊 27 °C 警告、橙色對齊 30 °C 告警，和感測器圓點一致
- 離最近感測器超過 4 m 的地方不推估（透明）；第一版**不考慮牆的阻隔**，牆兩側的感測器會互相影響
- 分析圖層（電力拓樸、溫度熱圖，之後的水路）一次只開一個，避免畫面混亂

### 11. 氣流（2026-10-17）

- dc-1f 是**冷通道封閉**加列間空調；氣流路徑由平面配置推算：空調前方 → 冷通道 → 機櫃正面 → 機櫃背面 → 排後方 → 空調後方
- 每台機櫃在 2 個高度各有一條循環，連到同排最近的列間空調（同排沒有時，用通道對面的）
- 以半透明「霧氣」呈現（使用者選擇，不用箭頭），冷藍到熱紅漸層；每團霧氣是濃的頭加上逐漸變淡變小的尾巴，用來表示流動方向；點選機櫃或空調時只顯示它參與的循環
- 是示意，不是 CFD 模擬；之後可接風扇轉速、機櫃功耗調整速度與顏色
- 約 2,000 個點（自訂 shader，每點各自的大小與透明度；每格只上傳位置與顏色），在測試機上總覽時開關幾乎沒有差異

## 第二張圖測試（dongguan，2026-10-15）

同一張「东莞机房」截圖，由兩個模型分別在新對話中照 workflow.md 做。兩邊都一次編譯通過、零警告，設備數量相同，排的順序和朝向判讀也相同。差異集中在兩件事：

| 問題 | 模型 A | 模型 B |
|---|---|---|
| 地板格不是正方形（橫 49.8 px、縱 43 px） | 自行擴充格式支援 `[x, z]` | 發現了，但統一用 50 px，縱向公尺數被壓縮約 14% |
| 圖示比例和真實規格矛盾（機櫃圖示約 650 mm 深） | 用標準 600 x 1200，通道剩 0.4 m，列成問題 | 機櫃縮成 500 x 600、每台加 100 mm gap，讓輪廓貼齊 |

結論：

- 疊圖對齊會掩蓋比例錯誤，因為資料和底圖用同一個 `pxPerTile`
- 沒有明確規則時，模型會傾向讓疊圖「看起來對」，而不是讓尺寸「實際上對」
- 一個模型改了程式，另一個沒改；流程需要明確規定格式不夠用時該怎麼做

已補進 workflow.md：比例兩個方向分開量、尺寸以真實規格為準、疊圖不能證明比例、格式不夠用時只記錄不修改，以及第 5 步的確認清單。

測試中也發現一個既有的 bug：UPS 沒有填 `capacityKVA`、電池櫃沒有填 `ups` 時，詳情面板會顯示 `undefined`（`src/ui/panel.js`）。

## 已知限制

- 排只支援橫排和直排，不支援斜放
- 房間只支援矩形；不規則形狀要用牆去拼
- 沒有柱子、樓梯這類物件，暫時用牆的矩形代替
- 一個案場只能有一層樓
- 平面圖品質影響很大：軟體截圖最好，照片或手繪圖誤差會比較大
- `pxPerTile` 只能填一個數字，不支援橫向、縱向比例不同的截圖
- 單獨設備（`equipment`）只能覆寫寬度，不能覆寫深度
- 沒有通用的「櫃子」類型，電表櫃、配電箱、設備箱只能借用 pdc / battery
- 詳情面板遇到缺少的屬性會顯示 `undefined`
